# База данных: переезд и что при этом важно

Бот подключается к обычному Postgres строкой `DATABASE_URL` — ничего специфичного для
конкретного облака в коде нет. Переезд поэтому сводится к одной переменной окружения, а вся
сложность лежит в двух местах: в форме строки подключения и в судьбе данных.

Redis (`REDIS_URL`) к переезду базы отношения не имеет и остаётся где стоял. В нём кэш,
кулдауны и квоты обращений к чужим API — данных, которые нельзя потерять, там нет.

## Сначала о данных

Схему бот создаёт сам: `MIGRATE_ON_START=true` (по умолчанию) применяет миграции при старте, и
пустая база через минуту становится готовой. **Данные же не переносятся сами** — это отдельная
работа, и делать её надо, пока старая база ещё отвечает.

Что теряется вместе с базой: история турниров, зал славы, уровни, монеты, достижения,
прогнозы, сохранённые форматы. Что восстанавливается само: привязки игровых аккаунтов и ранги
— игроки заново делают `/link`, ранги подтягиваются из API игр в течение получаса.

Перенести данные:

```sh
pg_dump --no-owner --no-privileges --format=custom "СТАРАЯ_СТРОКА" > dump.pgc
pg_restore --no-owner --no-privileges --dbname="НОВАЯ_СТРОКА" dump.pgc
```

`--no-owner --no-privileges` обязательны: в облачных базах владелец схемы называется иначе, и
без этих флагов восстановление спорит о правах вместо того, чтобы восстанавливать.

**Западня, из-за которой этот раздел вообще появился.** Если старая база отказала по квоте
тарифа, она не даёт соединения вообще — то есть снять дамп уже нельзя. Единственные выходы:
дождаться сброса квоты (у Neon вычислительное время обнуляется в начале расчётного периода)
либо на один месяц взять платный тариф ради одного `pg_dump`. Поэтому дамп снимают заранее, а
не когда прижало: в боте для этого есть `BACKUP_ENABLED=true` и джоба `maintenance:backup`.

## Проверить строку до переключения

```sh
npm run db:check -- "postgres://..."
```

Отвечает словами: пустила ли база, шифруется ли соединение, применены ли миграции, сколько
таблиц. Пароль в вывод не попадает — вывод пересылают, а строка подключения уезжает вместе с
ним.

Четыре исхода, которые выглядят одинаково в логе падений и лечатся по-разному:

| Что сказано | Что делать |
|---|---|
| база пустая | ничего, бот создаст таблицы при старте |
| база готова, миграций N | можно переключать |
| есть таблицы, но нет отметок о миграциях | строка ведёт не туда — это чужая база |
| не пустила / не отвечает / квота | разбираться с базой, а не с ботом |

## Supabase

Бесплатный тариф даёт 500 МБ и **не** ограничивает вычислительное время — именно этим он
отличается от Neon, где кончившиеся часы останавливают базу целиком. База бота весит единицы
мегабайт, так что 500 МБ хватит на годы.

Порядок такой:

1. Создать проект на supabase.com. Пароль базы задаётся при создании и показывается один раз.
2. Взять строку подключения: **Connect → Session pooler**. Она выглядит так:

   ```
   postgresql://postgres.<ref>:<пароль>@aws-1-<регион>.pooler.supabase.com:5432/postgres
   ```

3. Дописать в конец `?sslmode=verify-full`.
4. Проверить: `npm run db:check -- "строка"`. Ожидаемый ответ — «база пустая».
5. Прописать её как `DATABASE_URL` на хостинге бота и перезапустить. В логе должно появиться
   «миграции применены».
6. `/tournament formats` и остальные команды работают сразу: набор команд бот обновляет сам
   при старте.

Три вещи, на которых спотыкаются, и все три — про строку подключения:

- **Не прямое подключение, а pooler.** Прямой адрес (`db.<ref>.supabase.co`) у новых проектов
  доступен только по IPv6, а в контейнере хостинга IPv6 может не быть — получится
  `ENOTFOUND`. Session pooler работает по IPv4 и ведёт себя как обычное соединение.
- **Session pooler, а не transaction.** У transaction pooler порт 6543 и режим, в котором
  соединение отдаётся другому клиенту после каждой транзакции. Миграции и `pg_dump` в таком
  режиме работают ненадёжно. Нужен порт **5432** на хосте `pooler.supabase.com`.
- **Имя пользователя с точкой.** У pooler это `postgres.<ref>`, а не `postgres`. Если
  скопировать из прямого подключения, база не пустит, и `db:check` скажет «не подошли пароль,
  имя базы или прав недостаточно».

Пароль в строке должен быть закодирован для URL. Символы `@ : / ? # &` внутри пароля ломают
разбор строки: либо не используйте их, либо замените на `%40`, `%3A` и так далее.

## Про `sslmode`

Драйвер `pg` предупреждает при старте, что `require`, `prefer` и `verify-ca` сейчас работают
как `verify-full`, а в следующей крупной версии станут работать слабее. Чтобы поведение не
поменялось само при обновлении зависимостей, в строке лучше писать `sslmode=verify-full`
прямо — тогда и предупреждение уходит.

Если с `verify-full` соединение не устанавливается из-за сертификата, есть `sslmode=no-verify`:
шифрование остаётся, проверка удостоверяющего центра — нет. Это ослабление, а не настройка
удобства: с ним посредник между ботом и базой становится возможен. Брать его стоит только как
временную меру и понимая, чем платите.

## Свой Postgres в docker-compose

В репозитории есть `docker-compose.yml` со всем стеком: postgres, redis, одноразовый сервис
миграций, бот и caddy с TLS. Квот там нет по определению, бэкапы делает сам бот в
примонтированный том. Цена — своя машина, которую надо обслуживать, и бот в этом случае
уезжает с хостинга ботов.

Строка подключения внутри compose уже задана service-именами и не совпадает с той, что в
`.env` для локальной разработки: внутри контейнера `localhost` — это сам контейнер, и базы там
нет. Это самая частая причина `ECONNREFUSED` при первом запуске в контейнере.
