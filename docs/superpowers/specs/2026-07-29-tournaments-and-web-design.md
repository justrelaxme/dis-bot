# Турниры и веб-витрина — дизайн

Спек на этапы 5 (турниры) и 6 (веб-витрина) из декомпозиции
`docs/superpowers/specs/2026-07-27-discord-gaming-bot-design.md`. Этапы 2 (прогрессия),
3 (LFG) и 4 (модерация) отложены по решению владельца: сервер хочет проводить ивенты сейчас.

## 1. Задача

Провести на сервере турнир по Dota 2, LoL, TFT или Valorant так, чтобы организатор не сидел
весь вечер, вбивая результаты руками, а участники понимали, где они в сетке и с кем играют.
Плюс витрина в браузере: сетку из шестнадцати команд в сообщении Discord читать невозможно.

### Решения владельца, зафиксированные до проектирования

| Вопрос | Решение |
|---|---|
| Формат сетки | Single elimination. Движок закладывается так, чтобы double elimination и Swiss добавлялись без переписывания |
| Состав | И одиночки, и команды — режим объявляется при создании турнира |
| Результаты | Репортит участник, соперник подтверждает, администратор разбирает только спорные |
| Витрина | Публичная, **только чтение**: сетки, лидерборды, страницы профилей |
| Выбор дисциплины | Перед анонсом бот вывешивает временное голосование, по какой игре проводить турнир |
| Сбор команды | В Discord: карточка команды с кнопкой «Вступить», а не рассылка приглашений капитаном |
| Заполнение профиля | Форма в Discord (модальное окно). Ранги руками не вводятся никогда — они приходят из API игр |
| Ведение цикла | **Полностью автоматическое.** Бот сам, по расписанию, вывешивает голосование, объявляет условия, открывает регистрацию, создаёт каналы, строит сетку |
| Частота | **Ежедневно.** Голосование в 14:00 Europe/Berlin |
| Каналы команд | **Только голосовой** на команду, пускает лишь её состав. Ссылки и пароли лобби идут во встроенный чат голосового канала |
| Мало команд | **Проводится всё равно**, но называется по размеру: две команды — шоуматч, а не турнир. Отмена только если играть физически некому (меньше двух) |

### Вне скоупа

- Призовой фонд, платежи, взносы за участие.
- Автоматическое определение исхода по API игры. По Valorant рангов нет вовсе, а надёжно
  сопоставить конкретный матч с парой турнирной сетки не выйдет ни в одной из четырёх игр:
  бот не знает, какая из десяти сегодняшних игр была турнирной.
- Вход в витрину, редактирование настроек из браузера, панель администратора.
- Стримы, оверлеи для OBS, интеграция с площадками вроде Challonge.
- Расписание по времени с автостартом матчей. Организатор стартует раунды сам.

## 2. Зависимости и что уже готово

Этап 1 (личность и профиль) даёт то, без чего турниры не собрать:

- **привязка игрового аккаунта с подтверждением владения.** Регистрация в турнире требует
  подтверждённой привязки по нужной игре — иначе в сетку попадают чужие смурфы и выдуманные ники.
  Признак подтверждённости — `verified_at IS NOT NULL` в `game_accounts`.
- **ранги и `rankScore`.** Из них делается жеребьёвка по силе, чтобы фавориты не встретились в
  первом круге.
- **`GameProvider` и реестр провайдеров** — оттуда берутся отображаемые имена и ранги.
- **шина событий, кулдауны, кэш, лимитер, HTTP-сервер на Fastify** — всё из ядра этапа 0.

Прогрессия (этап 2) в исходной декомпозиции была зависимостью турниров: предполагалось, что
за победу дают опыт и валюту. Раз этап 2 отложен, награды выносятся в отдельное событие
`tournament.finished`, на которое прогрессия подпишется, когда появится. Турнир работает без неё.

## 3. Модель данных

Общие правила проекта в силе: снежинки Discord — `text`, времена — `timestamptz` UTC,
внешние ключи с `on delete cascade`, миграции только вперёд.

### Игра турнира — не то же, что провайдер

`ProviderId` описывает источник данных (`steam`, `riot-lol`, `riot-tft`, `riot-valorant`),
а турнир проводится по **игре**. Это разные вещи: Dota 2 обслуживается провайдером `steam`,
а турнир можно объявить и по игре, для которой провайдера нет вовсе.

```ts
type TournamentGame = 'dota2' | 'lol' | 'tft' | 'valorant' | 'other';
```

Для `'other'` не работают ни требование подтверждённой привязки, ни жеребьёвка по рангу —
организатор проводит турнир на честном слове, и это законный сценарий.

### `tournament_entrants` — единое понятие для одиночек и команд

Ключевое решение всей модели. Сетка сводит **участников**, а участник это либо один игрок,
либо команда. Развилка «соло или команда» живёт только в регистрации; движок сетки,
продвижение победителя и репорт результатов о ней ничего не знают.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | serial pk | |
| `tournament_id` | int fk | |
| `display_name` | text | ник игрока или название команды |
| `captain_user_id` | text | для соло — он же и есть участник |
| `seed` | int nullable | заполняется при старте |
| `checked_in_at` | timestamptz nullable | |
| `withdrawn_at` | timestamptz nullable | снятие не удаляет строку: сетка уже могла быть построена |

Уникальность: `(tournament_id, display_name)` и `(tournament_id, captain_user_id)`.

### `tournament_entrant_members`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | serial pk | |

Уникальность: `(entrant_id, user_id)` и — важнее — `(tournament_id, user_id)`. Второе ограничение
и есть причина держать здесь `tournament_id`: без него «один человек не может играть за две команды
одного турнира» пришлось бы проверять запросом, а проверка запросом означает гонку между двумя
одновременными вступлениями. Пусть это гарантирует база.

Для `entry_mode = 'solo'` у участника ровно одна строка с ролью `'captain'`.

Продвижение победителя вычисляется, а не хранится: матч круга `r`, слот `s` ведёт в матч
круга `r + 1`, слот `floor(s / 2)`, в сторону `a` при чётном `s` и `b` при нечётном. Хранить
ссылку на родителя значит иметь второй источник истины о форме сетки.

### `tournament_match_reports`

Каждый репорт и каждое решение — отдельной строкой: кто, что заявил, когда, и было ли это
решением администратора. Нужно для разбора споров, а не для отображения.

## 4. Как это работает

### Голосование по дисциплине — шаг перед турниром

Организатор не угадывает, во что сервер хочет играть, а спрашивает. `/tournament poll`
вывешивает **нативное голосование Discord** (проверено: discord.js 14.27 отдаёт его полем
`poll` в сообщении, есть событие `messagePollVoteAdd`; минимальная длительность — час) со
списком дисциплин и длительностью, которую задал организатор.

Голосование привязывается к строке в `tournament_polls`, иначе оно останется картинкой: бот
должен уметь по закрытии прочитать итог. По истечении срока бот объявляет победившую дисциплину
и предлагает создать турнир по ней — **предлагает, а не создаёт**. Бот, который сам объявил
турнир по итогам голосования, однажды объявит его не тогда, когда этого ждали.

Голосование живёт своей жизнью и турнир не блокирует: организатор вправе создать турнир и без
него. Опрос — способ выбрать дисциплину, а не обязательная ступень.

`tournament_polls`: `id`, `guild_id`, `message_id`, `channel_id`, `options` (jsonb — список
дисциплин), `closes_at`, `winner_game` (nullable, заполняется по закрытии), `created_by`.
Закрытие проверяет тот же планировщик, что и синхронизацию рангов: таймер в памяти не переживёт
перезапуск процесса, а голосование на сутки переживёт его почти наверняка.

### Автоматический цикл — бот ведёт день сам

Организатор ничего не нажимает. Раз в сутки бот проходит цикл целиком:

| Время (Europe/Berlin) | Что делает бот |
|---|---|
| 14:00 | вывешивает голосование по дисциплине на 2 часа |
| 16:00 | объявляет победившую игру, условия участия и что сделать, чтобы попасть; открывает регистрацию |
| 20:00 | закрывает регистрацию, создаёт голосовые каналы командам, строит сетку, объявляет первый круг |
| дальше | матчи репортятся и подтверждаются сами; по последнему матчу объявляет победителя и убирает каналы |

Времена — не константы в коде, а строки в `tournament_schedules`: ежедневный автомат, время
которого нельзя поменять без правки кода и перезапуска, придётся править в первый же день,
когда окажется, что в 20:00 на сервере никого.

Планировщик — тот же `croner` с `protect: true`, на котором работает синхронизация рангов.
Часовой пояс задаётся явно: сервер может стоять в UTC, а «14:00» имеется в виду местное.

**Объявление условий — это отдельный шаг, а не приписка.** В 16:00 бот пишет: какая игра
выбрана, до какого времени регистрация, сколько человек в команде, нужна ли подтверждённая
привязка, как собрать команду (карточка с кнопкой «Вступить»), как записаться. Игрок, который
зашёл на сервер впервые, должен понять, что делать, из одного сообщения — иначе автоматизация
экономит время организатора и тратит время игроков.

### Защиты, без которых автомат однажды сделает не то

Автомат без присмотра — это не «то же самое, но без команд», это другой класс рисков. Четыре
обязательны, и закладываются сразу: дописывать защиту к работающему автомату значит сначала
один раз получить последствия.

1. **Новый цикл не начинается, пока не закрыт предыдущий.** Ежедневный турнир, который не
   успели добить вечером, встретится с завтрашним голосованием — и участники окажутся в двух
   сетках сразу. Если вчерашний турнир ещё `running`, сегодняшний цикл не стартует, а пишет
   об этом в канал.
2. **Выключатель.** `tournament_schedules.enabled` — одно поле, которым администратор
   останавливает автомат, не выключая бота. Праздники, каникулы, ремонт сервера — поводы
   найдутся, и в этот момент выключателя ищут, а не пишут.
3. **Пауза, когда никто не приходит.** Несколько дней подряд без участников — расписание
   встаёт само, с объяснением.
4. **Идемпотентность дня.** Перезапуск процесса, наложение прогонов, повторная доставка —
   всё это не должно давать два голосования за один день. Уникальность `(guild_id, cycle_date)`
   в `tournament_cycles` гарантирует это базой, а не проверкой запросом: проверка запросом
   означает гонку между двумя прогонами.

`tournament_cycles`: `id`, `guild_id`, `cycle_date` (date), `stage`
(`'poll'`, `'registration'`, `'running'`, `'finished'`, `'skipped'`), `poll_id` (nullable),
`tournament_id` (nullable), `skip_reason` (nullable — почему день пропущен), `created_at`.
Уникальность по `(guild_id, cycle_date)`.

Эта таблица — ещё и ответ на вопрос «что вообще было вчера»: без неё разбирать, почему турнира
не случилось, придётся по логам.

### Жизненный цикл турнира

```
                    ┌─ /tournament poll ─> голосование ─> итог ─> предложение создать
                    │                                                      │
                    │                                                      v
draft ──open──> registration ──start──> running ──последний матч──> finished
  │                   │                    │
  └──────────────── cancel ────────────────┘
```

- **draft** — турнир создан, не виден участникам. Организатор проверяет параметры.
- **registration** — открыта запись. Проверки при регистрации: свободные места, состав
  нужного размера, подтверждённая привязка по игре у каждого игрока (если включено),
  никто из состава не занят в другом участнике этого турнира.
- **start** — жеребьёвка, построение сетки, создание веток под матчи первого круга.
  После старта регистрация закрыта навсегда: пересобирать сетку на ходу — значит терять
  уже сыгранные результаты.
- **running** — матчи репортятся и подтверждаются, победители продвигаются.
- **finished** — победитель определён, публикуется `tournament.finished`.

### Сетка и жеребьёвка

Размер сетки — ближайшая сверху степень двойки от числа участников. Недостающие места
занимают **пропуски** (bye), и распределяются они старшим сеяным: пропуск это преимущество,
и отдавать его случайно — значит обесценить жеребьёвку по рангу.

Жеребьёвка `'rank'` использует `rankScore` из этапа 1: для команды берётся средний скор
состава по нужной игре. Игроки без ранга считаются нулём — так порог «выше unranked»
работает сам собой. Жеребьёвка `'random'` перемешивает участников; сид всё равно
записывается, чтобы сетка была воспроизводима и её можно было показать.

Стандартная расстановка сеяных по слотам первого круга (1 против последнего, 2 против
предпоследнего и так далее) — не украшение: без неё два сильнейших встречаются в первом круге,
и весь смысл сеяния пропадает.

### Репорт результата

```
матч готов (оба участника известны)
        │
        ├─ участник вызывает /match report <победитель>
        │        │
        │        ├─ соперник подтверждает ──> confirmed ──> победитель продвинут
        │        ├─ соперник спорит ────────> disputed ──> решает администратор
        │        └─ соперник молчит 60 минут ─> confirmed автоматически
        │
        └─ соперник не явился ──> организатор даёт walkover
```

Автоподтверждение через 60 минут — обязательное свойство, а не удобство: без него один
неотвечающий игрок останавливает всю сетку, и турнир упирается в присутствие организатора
ровно так же, как если бы результаты вбивал он.

Репортить может любой игрок любого из двух участников, подтверждать — любой игрок
**другого** участника. Тот же человек не может и заявить, и подтвердить: проверка идёт по
составу, а не по тому, кто нажал кнопку.

Спор не разрешается ботом никогда. Администратор вызывает `/match resolve` и назначает
победителя; в `tournament_match_reports` остаётся, что это было решение администратора.

### Название по размеру, а не отмена

Порога «меньше четырёх — отменяем» нет. При полном автомате бот проводит то, что собралось,
а не отказывает людям, которые пришли. Меняется только слово, которым он это называет:

| Участников | Как называется | Что это по сути |
|---|---|---|
| 0-1 | не проводится | играть некому: один участник не с кем не сыграет |
| 2 | шоуматч | один матч, сетки нет |
| 3-4 | мини-турнир | сетка на 4 слота, один-два пропуска |
| 5 и больше | турнир | обычная сетка |

Название влияет **только на текст объявлений и на витрину**. Механика одна и та же: сетка,
репорт, подтверждение, продвижение победителя. Заводить два разных движка ради двух команд —
это два места, где может разойтись поведение, вместо одного.

Если играть некому несколько дней подряд, расписание встаёт на паузу с объяснением в канал.
Бот, который каждый день сообщает «никто не пришёл», перестаёт читаться уже на третий раз, и
тогда его перестают читать и в тот день, когда пришли.

### Комнаты: две разных, и одна другую не заменяет

**Голосовой канал команды.** Создаётся на каждую зарегистрированную команду при закрытии
регистрации, права выданы только её составу (`PermissionOverwrites`: всем — запрет
`ViewChannel` и `Connect`, участникам команды — разрешение). Живёт весь турнир: там команда
сидит, пока играет. Ссылки на лобби и пароли идут во **встроенный чат голосового канала** —
отдельный текстовый канал на команду не нужен.

**Комната матча.** Каналы команд приватные, поэтому соперники друг с другом связаться не могут
— а им надо: договориться о лобби, пароле, времени, о переносе. Значит нужна вторая комната,
куда пускает **обе** команды пары. Это приватная ветка в общем канале турнира: ветки дешевле
по лимитам Discord, сами архивируются и живут ровно столько, сколько идёт матч. При
подтверждении результата ветка архивируется.

### Уборка обязательна, а не желательна

Турнир на 16 команд — это 16 голосовых каналов плюс ветки матчей. У Discord есть лимит
каналов на сервер, и без уборки сервер за месяц ежедневных турниров превратится в свалку.
Поэтому: по завершении или отмене турнира каналы команд удаляются, ветки архивируются.
Удаление идёт по записанным в БД идентификаторам, а не по имени канала — имя администратор
может переименовать, и тогда уборка либо не найдёт нужное, либо снесёт чужое.

Если канал уже удалён руками, уборка это не считает ошибкой. Если удалить не удалось (нет
прав), это логируется, и турнир всё равно закрывается: незакрытый из-за канала турнир
заблокировал бы завтрашний цикл.

Отказ Discord при **создании** канала тоже не отменяет турнир: матч играется и репортится
без комнаты. Комната — удобство, а не носитель состояния.

## 5. Команды

Организаторские (право «Управление сервером»):

- `/tournament create` — имя, игра, режим, размер состава, максимум участников, жеребьёвка,
  число карт в матче (`best_of`: 1, 3 или 5; по умолчанию 1 и применяется ко всем матчам турнира)
- `/tournament open` / `/tournament close` — регистрация
- `/tournament start` — жеребьёвка и сетка
- `/tournament cancel`
- `/match resolve` — решение по спорному матчу
- `/match walkover` — неявка

Участникам:

- `/team create` / `/team invite` / `/team kick` / `/team leave` / `/team disband` — только в командном режиме
- `/tournament join` / `/tournament leave`
- `/checkin`
- `/match report`
- `/bracket` — компактный вид и ссылка на витрину

Все ответы эфемерные, кроме объявлений раундов. Всё, что ходит в БД или в Discord API,
объявляет `defer`: окно интеракции — три секунды.

## 6. События

```ts
'tournament.created':  { tournamentId: number; guildId: string; game: string }
'tournament.started':  { tournamentId: number; guildId: string; entrants: number }
'tournament.finished': { tournamentId: number; guildId: string; winnerEntrantId: number; winnerUserIds: string[] }
'match.ready':         { tournamentId: number; matchId: number; round: number }
'match.confirmed':     { tournamentId: number; matchId: number; winnerEntrantId: number }
```

Провайдер и игра передаются строками: ядро не может импортировать типы модулей, иначе
зависимость перевернётся. `winnerUserIds` в `tournament.finished` — чтобы прогрессия, когда
появится, могла выдать награды, не заглядывая в таблицы турниров.

## 7. Веб-витрина

### Чем она является и чем нет

Витрина только **показывает**. Ни одного действия, ни одной формы, ни входа. Всё управление
остаётся в Discord. Это решение владельца, и оно же убирает целый класс работы: авторизацию,
сессии, проверку прав на сервере, CSRF.

### Устройство

Fastify в проекте уже есть (`/healthz`, `/metrics`, колбэк Steam) — витрина живёт в нём же,
отдельным модулем. Страницы отдаются **готовым HTML с сервера**, без SPA и без сборки фронтенда:
для страниц, на которых нечего нажимать, одностраничное приложение — это лишний слой,
лишний шаг сборки и лишний способ сломаться.

Маршруты:

| Маршрут | Что показывает |
|---|---|
| `/t/:id` | сетка турнира: круги, пары, счёт, победители |
| `/t/:id/entrants` | участники и составы |
| `/leaderboard/:game` | таблица по `rankScore`, только подтверждённые привязки |
| `/p/:userId` | профиль: привязки, ранги, история изменений, турнирные результаты |
| `/` | список активных и прошедших турниров |

Сетка рисуется CSS-гридом с абсолютным позиционированием линий — без библиотек и без канваса.
Работать обязана на телефоне: половина участников откроет ссылку с него.

### Приватность

Витрина публична, поэтому на ней не может быть ничего, чего игрок не показывал сам:

- только подтверждённые привязки (`verified_at IS NOT NULL`);
- никогда не показываются `discord_id`, содержимое личных сообщений, аудит-лог модерации;
- профиль доступен по идентификатору Discord, но **имя и аватар берутся из БД бота**, а не
  запрашиваются у Discord в момент показа: иначе витрина превращается в способ пробить
  произвольный аккаунт через наш сервер;
- у игрока должна быть возможность скрыть свою страницу. Флаг `profile_public` в таблице
  `users` (она из этапа 0), по умолчанию **выключен**, включается командой. Публиковать чужие
  ранги без спроса нельзя, даже если они и так видны в игре. Участие в турнире — согласие
  на показ в сетке под тем именем, под которым записался, и не более того.

Кэш готовых страниц в Redis на 60 секунд: сетка меняется редко, а по ссылке из объявления
о турнире придут все сразу.

## 8. Ошибки и надёжность

Три класса ошибок из этапа 0 в силе: `UserError` (текст показывается как есть),
`ProviderError` (сервис игры недоступен), всё остальное (код инцидента в лог).

Специфика турниров:

- **Продвижение победителя обязано быть идемпотентным.** Двойное нажатие кнопки
  подтверждения, повторная доставка взаимодействия, гонка автоподтверждения с ручным —
  всё это реально. Продвижение выполняется в транзакции с проверкой текущего состояния матча.
- **Сетка не пересобирается после старта** ни при каких условиях. Снятие участника даёт
  его сопернику walkover, а не сдвиг сетки.
- **Отказ Discord API не отменяет результат.** Если победитель записан, а объявление
  отправить не удалось, результат остаётся записанным.
- Витрина, не сумевшая нарисовать страницу, отдаёт понятную заглушку, а не трассировку стека
  и не JSON с внутренним текстом.

## 9. Тестирование

Как на этапах 0 и 1: юнит-тесты на чистую логику, интеграционные на настоящем Postgres.

Что обязано быть покрыто, потому что цена ошибки высока:

- жеребьёвка: пропуски достаются старшим сеяным; сеяные расставлены так, что первый и второй
  встречаются не раньше финала; воспроизводимость при том же входе;
- продвижение: победитель попадает в правильный слот следующего круга при чётном и нечётном
  слоте; двойное подтверждение не продвигает дважды;
- репорт: тот же человек не может заявить и подтвердить; спор не разрешается сам;
  автоподтверждение срабатывает по истечении окна и не срабатывает раньше;
- регистрация: один человек не в двух командах; неподтверждённая привязка не проходит,
  когда это требуется; переполнение не пускает;
- витрина: скрытый профиль не отдаётся; неподтверждённые привязки не попадают в лидерборд.

## 10. Критерии готовности

**Турниры.** Организатор создаёт турнир на 8 команд по 5 человек, открывает регистрацию,
команды собираются и записываются, старт строит сетку с жеребьёвкой по рангу, участники
репортят и подтверждают результаты, спорный матч разбирает администратор, победитель
определён, событие о завершении опубликовано. Всё — не выходя из Discord.

**Витрина.** Ссылка из объявления открывает сетку этого турнира на телефоне, лидерборд
показывает только подтверждённые привязки, скрытый профиль не отдаётся.
