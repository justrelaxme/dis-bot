# Discord-бот игрового сообщества — дизайн

Дата: 2026-07-27
Статус: согласован, готов к планированию
Детальный скоуп этого документа: **этап 0 (ядро) + этап 1 (личность и профиль)**

---

## 1. Задача

Discord-бот для игрового сервера, объединяющий в одной системе игровые интеграции,
поиск тиммейтов, прогрессию сообщества, модерацию, турниры и веб-дашборд.

Ценность, недостижимая набором готовых ботов: **единая база**. XP зависит от игровой
активности, LFG знает ранг игрока, турнирный сидинг берёт рейтинг из профиля. Именно
эта связность — причина писать своё, а не собирать из MEE6, Apollo и Tatsu.

### Целевая среда

| Параметр | Значение |
|---|---|
| Серверов | один |
| Участников | до ~5 000 |
| Игры | Dota 2 и Steam-игры, Riot (LoL / Valorant / TFT), прочие — без глубокой статы |
| Язык интерфейса | русский (строки вынесены в отдельный слой) |
| Хостинг | один VPS, Docker Compose |
| Шардинг | не требуется (обязателен с 2 500 серверов) |

### Вне скоупа

Осознанно исключено. Каждый пункт — решение, а не упущение.

- **Музыка и голосовое аудио.** Требует отдельного Lavalink-сервера, несёт юридические
  риски (Google закрывал крупные музыкальные боты), готовые решения лучше.
- **AI/LLM-фичи.** Не решают ни одной из заявленных болей, добавляют стоимость за запрос
  и класс отказов, который нечем компенсировать.
- **Реальные платежи и донат-магазин.** Только виртуальная валюта. Платежи — это
  бухгалтерия, споры и возвраты, а не фича бота.
- **Мультиязычность.** Только русский. Строки лежат отдельным слоем, поэтому добавление
  языка позже — работа переводчика, а не рефакторинг.
- **Продуктовая поддержка нескольких серверов.** При этом `guild_id` присутствует в схеме
  с первого дня: это почти бесплатно и снимает болезненную миграцию, если решение изменится.

## 2. Декомпозиция

Шесть подсистем в один план не укладываются. Каждый этап после сдачи даёт работающую
ценность самостоятельно.

| Этап | Под-проект | Результат | Зависит от |
|---|---|---|---|
| 0 | Ядро и каркас | Бот в сети, `/ping`, БД, миграции, конфиг, логи, тесты, деплой | — |
| 1 | Личность и профиль | Привязка Steam/Riot с верификацией, карточка профиля, авто-роли по рангу | 0 |
| 2 | Прогрессия | XP за активность, уровни, экономика, ачивки, лидерборды, сезоны | 0, 1 |
| 3 | LFG и лобби | Сбор пати по игре/режиму/рангу, авто-голосовые каналы, очереди | 0, 1 |
| 4 | Модерация | Антиспам, антирейд, варны с историей, тикеты, аудит-лог | 0 |
| 5 | Турниры | Регистрация, сетки, репорт результатов, каналы под матчи | 0, 1, 2 |
| 6 | Веб-дашборд | Настройки, лидерборды, логи модерации в браузере | все выше |

Этап 1 стоит вторым потому, что прогрессия, LFG и турниры все задают один вопрос:
«кто этот игрок и какой у него ранг». Модерация независима и может быть переставлена
куда угодно после этапа 0.

Этапы 2–6 получат собственные спеки и планы. Ниже детализируются только 0 и 1.

## 3. Архитектура

Выбран **модульный монолит**: один Node-процесс, тонкое ядро плюс модули-фичи.

Отклонённые варианты:

- **Event-driven микросервисы** (gateway отдельно, воркеры через Redis Streams/NATS) —
  оверинжиниринг для 5 000 участников. Платим распределёнными транзакциями и отладкой
  по трём логам за масштабирование, которое не понадобится.
- **Сборка из готовых ботов** — быстро на старте, но пять несвязанных баз данных делают
  недостижимой ровно ту связность, которая является целью проекта.

### Стек

| Компонент | Выбор | Причина |
|---|---|---|
| Runtime | Node.js 22 LTS | требуется `vitest` (`^20 \|\| ^22 \|\| >=24`), покрывает discord.js (`>=18`) |
| Язык | TypeScript, strict | строгая типизация на большой кодовой базе |
| Discord | discord.js 14.27.x | первым получает новые API, 100% покрытие Discord API |
| БД | PostgreSQL 16 | источник истины |
| ORM | Drizzle ORM 0.45.x + drizzle-kit 0.31.x | типобезопасный SQL без бинарного движка, простой escape hatch для лидербордов |
| Кэш/очереди | Redis 7 (ioredis 5.x) | кэш провайдеров, token bucket, распределённые локи |
| Логи | pino 10.x | структурированный JSON |
| Валидация | zod 4.x | конфиг и внешние ответы |
| Тесты | vitest 4.x + Testcontainers | unit + интеграционные на реальном Postgres |
| HTTP | Fastify | `/healthz`, `/metrics`, OAuth-callback; вырастает в дашборд на этапе 6 |
| Деплой | Docker multi-stage + Compose + Caddy | TLS автоматом, четыре сервиса |

Версии зафиксированы на дату документа и проверены в npm-реестре.

### Ядро

Ядро — 300–400 строк, которые дальше не меняются. Оно не знает о модулях ничего.

```
src/

    client.ts          # создание Client, интенты
    module.ts          # контракт BotModule
    registry.ts        # загрузка модулей, сбор команд/событий/джоб
    config.ts          # zod-валидация env: падаем на старте, не в рантайме
    db/
      client.ts        # пул Postgres
      schema/          # схемы модулей собираются здесь
      migrations/      # версионированный SQL от drizzle-kit
    cache.ts           # Redis
    logger.ts          # pino
    http/              # Fastify: /healthz, /metrics, callbacks
    commands/router.ts # маршрутизация interactionCreate, граница ошибок
    events/bus.ts      # типизированная внутренняя шина
    scheduler.ts       # cron-джобы, объявленные модулями
    errors.ts          # UserError / ProviderError / BugError
    ui/                # пагинация, подтверждения, единый стиль карточек
  modules/
    ping/              # эталонный модуль — образец для последующих
    identity/          # этап 1
      index.ts         # манифест
      commands/        # link.ts, unlink.ts, profile.ts, ranksync.ts
      providers/       # provider.ts (интерфейс), steam.ts, riot-lol.ts, riot-tft.ts, riot-valorant.ts
      services/        # linking.ts, rank-sync.ts, role-mapping.ts

      render/          # profile-card.ts
  shared/              # чистые утилиты, ноль зависимостей от ядра

```

### Контракт модуля

```ts
export interface BotModule {
  name: string;
  commands?: CommandDefinition[];
  events?: EventHandler[];
  jobs?: ScheduledJob[];
  setup?(ctx: ModuleContext): Promise<void>;
  teardown?(): Promise<void>;
}

export interface ModuleContext {
  client: Client;
  db: Database;
  cache: Cache;
  logger: Logger;
  bus: EventBus;
  config: Config;
}
```

Два правила, от которых зависит тестируемость и возможность декомпозиции:

**Зависимости приходят аргументом, а не глобальным импортом.** Модуль, получающий
`ModuleContext`, тестируется с фейковым контекстом без живого Discord и без живой БД.
Модуль, делающий `import { db }`, не тестируется никак.

**Модули общаются через шину, а не через прямые импорты.** `identity` публикует
`rank.changed`, `progression` его слушает, друг о друге они не знают. Без этого через
три модуля получается клубок перекрёстных импортов и декомпозиция из раздела 2
становится нарисованной, а не настоящей.

Команды объявляются данными (`CommandDefinition`), а не декораторами — так их проще
тестировать и перечислять.

### Почему свой каркас, а не Sapphire

Sapphire — приличный фреймворк, он сэкономил бы препроцессоры и парсинг аргументов.
Но объём того, что он делает за нас, — это как раз те 300 строк ядра, а взамен он
навязывает конвенции, которые придётся учить и местами обходить. Для проекта, растущего
шестью модулями, предпочтительнее каркас, который целиком держится в голове.

### Интенты

Принцип минимальных привилегий: интент включается тогда, когда появляется модуль,
который его использует.

| Интент | Когда | Привилегированный |
|---|---|---|
| `Guilds` | этап 0 | нет |
| `GuildMembers` | этап 0 (авто-роли) | да |
| `MessageContent` | этап 4 (модерация) | да |
| `GuildVoiceStates` | этап 3 (LFG) | нет |
| `GuildPresences` | только если решим читать Rich Presence | да |

Для бота на одном сервере привилегированные интенты включаются тумблером в Developer
Portal без верификации (порог — 100 серверов).

## 4. Модель данных

### Общие правила

- **Snowflake-идентификаторы Discord хранятся в `text`.** JS-число их не вмещает, а
  `bigint` тянет BigInt в JSON-сериализацию. Текст однозначен.
- **Все времена — `timestamptz` в UTC.**
- **XP, валюта, LP — целые числа.** Никогда float.
- **Миграции только вперёд**, версионированные SQL-файлы, применяются отдельным шагом
  до старта бота.

### Этап 0

```
guilds
  id            text PK              -- Discord guild snowflake
  settings      jsonb NOT NULL DEFAULT '{}'
  created_at    timestamptz NOT NULL DEFAULT now()

users
  id            text PK              -- Discord user snowflake
  created_at    timestamptz NOT NULL DEFAULT now()

members
  guild_id      text NOT NULL REFERENCES guilds(id)
  user_id       text NOT NULL REFERENCES users(id)
  joined_at     timestamptz NOT NULL
  PRIMARY KEY (guild_id, user_id)

audit_log
  id            bigserial PK
  guild_id      text NOT NULL
  actor_id      text                 -- NULL = действие бота
  action        text NOT NULL        -- 'account.linked', 'role.granted', ...
  target_id     text
  details       jsonb NOT NULL DEFAULT '{}'
  created_at    timestamptz NOT NULL DEFAULT now()
  INDEX (guild_id, created_at DESC)
```

`audit_log` появляется уже на этапе 0, хотя полноценно понадобится модерации на
этапе 4: универсальная таблица стоит дешево, а задним числом восстановить историю
действий невозможно.

### Этап 1

```
game_accounts
  id                   bigserial PK
  user_id              text NOT NULL REFERENCES users(id)
  provider             text NOT NULL          -- ProviderId, см. §5
  external_id          text NOT NULL          -- SteamID64 | Riot PUUID | Riot ID (valorant)
  display_name         text NOT NULL          -- persona | gameName#tagLine
  region               text                   -- платформа Riot; NULL для Steam
  verified_at          timestamptz            -- NULL = не подтверждён
  verification_method  text NOT NULL          -- 'steam-openid' | 'riot-third-party-code' | 'manual'
  created_at           timestamptz NOT NULL DEFAULT now()
  updated_at           timestamptz NOT NULL DEFAULT now()
  UNIQUE (provider, external_id)
  UNIQUE (user_id, provider)

account_verifications
  id            bigserial PK
  user_id       text NOT NULL REFERENCES users(id)
  provider      text NOT NULL
  challenge     text NOT NULL          -- код или OpenID nonce
  payload       jsonb NOT NULL DEFAULT '{}'
  attempts      int NOT NULL DEFAULT 0
  expires_at    timestamptz NOT NULL
  created_at    timestamptz NOT NULL DEFAULT now()
  INDEX (user_id, provider)

rank_snapshots
  id            bigserial PK
  account_id    bigint NOT NULL REFERENCES game_accounts(id) ON DELETE CASCADE
  mode          text NOT NULL          -- 'solo-duo' | 'flex' | 'tft-ranked' | 'dota-mmr' | 'val-competitive'
  scale         text NOT NULL          -- 'riot-tier' | 'dota-mmr'
  tier          text                   -- 'PLATINUM'; NULL для числовых шкал
  division      text                   -- 'II'; NULL где нет делений
  points        int                    -- LP или MMR
  raw           jsonb NOT NULL         -- исходный ответ провайдера
  captured_at   timestamptz NOT NULL DEFAULT now()
  INDEX (account_id, mode, captured_at DESC)

role_mappings
  id            bigserial PK
  guild_id      text NOT NULL REFERENCES guilds(id)
  provider      text NOT NULL
  mode          text NOT NULL
  tier          text NOT NULL
  role_id       text NOT NULL          -- Discord role snowflake
  UNIQUE (guild_id, provider, mode, tier)
```

### Три ограничения, заслуживающие объяснения

**`UNIQUE (provider, external_id)`** — один игровой аккаунт нельзя привязать к двум
Discord-профилям. Без этого система рангов и лидербордов накручивается за вечер.

**`UNIQUE (user_id, provider)`** — один игровой аккаунт на провайдера. Это сознательный
отказ от поддержки смурфов: авто-роль по рангу требует однозначного ответа на вопрос
«какой у него ранг», а с тремя привязанными аккаунтами это становится продуктовым
решением, которое сейчас нет смысла принимать. Если смурфы понадобятся — добавляется
колонка `is_primary`, а не переделывается схема.

**`rank_snapshots` как временной ряд, а не поле «текущий ранг»** — иначе невозможны
«ты поднялся с Gold на Platinum», графики роста и сезонные итоги. Стоит одной таблицей.
Текущий ранг — последняя запись по `(account_id, mode)`.

## 5. Игровые интеграции

### Интерфейс провайдера

```ts
type ProviderId = 'steam' | 'riot-lol' | 'riot-tft' | 'riot-valorant';

interface GameProvider {
  id: ProviderId;
  capabilities: {
    verification: 'steam-openid' | 'riot-third-party-code' | 'none';
    rank: 'api' | 'manual';   // 'manual' = ранг вводит пользователь
  };
  startVerification?(userId: string): Promise<VerificationChallenge>;
  completeVerification?(challenge: VerificationChallenge): Promise<VerifiedAccount>;
  fetchProfile(externalId: string): Promise<GameProfile>;
  fetchRank?(externalId: string): Promise<RankInfo[]>;
}

interface RankInfo {
  mode: string;
  scale: 'riot-tier' | 'dota-mmr';
  tier: string | null;
  division: string | null;
  points: number | null;
  source: 'api' | 'manual';
  raw: unknown;
}
```

Авто-роли, лидерборды и будущий турнирный сидинг работают только с `RankInfo` и не знают
специфики Riot или Dota. Новая игра — новая реализация интерфейса, ничего больше.

Поле `capabilities` существует ради Valorant: у него нет ни публичного API, ни способа
подтвердить владение аккаунтом, поэтому методы верификации и `fetchRank` у него
отсутствуют, а ранг приходит из ручного ввода. Без явного объявления возможностей код
авто-ролей и синхронизации пришлось бы усыпать проверками `if (provider.id === ...)`.

### Доступность данных по играм — честная картина

| Игра | API | Верификация владения | Риск |
|---|---|---|---|
| Steam-игры (профиль, библиотека, часы) | Steam Web API, ключ за минуты | Steam OpenID | низкий |
| Dota 2 (матчи, MMR-оценка) | Steam Web API + OpenDota | через Steam | средний: история читается только при открытых настройках приватности |
| LoL / TFT (ранг, матчи) | Riot API, нужен production-ключ | `third-party-code` в клиенте | средний: dev-ключ живёт 24 часа, production выдаётся по заявке с ревью |
| Valorant | публичного официального API нет | невозможна | высокий: только ручной ввод ранга |

**Riot production-ключ — внешняя зависимость проекта.** Dev-ключ протухает каждые
24 часа и в проде неприменим. Заявка на production проходит ревью Riot, срок и результат
не гарантированы. Этап 1 сдаётся без него: Steam работает полностью, Riot-провайдеры
реализованы и покрыты тестами на моках, а включаются по факту получения ключа.

**Riot переводит API на PUUID и выпиливает `encryptedSummonerId`,** на котором
исторически висел эндпоинт `third-party-code`. На реализации сверяемся с актуальной
документацией. Если механизм окажется недоступен — fallback: ручной ввод Riot ID с
проверкой совпадения имени и явной пометкой «не подтверждено» в профиле
(`verified_at = NULL`, `verification_method = 'manual'`). Неподтверждённые аккаунты
не дают авто-роль.

**Valorant** поддерживается только через ручной ввод ранга: провайдер `riot-valorant`
имеет `capabilities.rank = 'manual'` и `verification = 'none'`. Ранг попадает в
`rank_snapshots` с `source = 'manual'`, фоновая синхронизация его не трогает, авто-роль
он не даёт. Ручной ранг помечается в карточке профиля как заявленный игроком и
запрашивается заново при смене сезона.

Неофициальные обёртки над Valorant (HenrikDev и подобные) отклонены: серая зона ToS и
отключение в любой момент без предупреждения. Если позже решим принять этот риск —
это добавление ещё одной реализации `GameProvider`, схема не меняется.

### Верификация Steam и HTTP-сервер

Ядро на этапе 0 поднимает Fastify — он всё равно нужен для `/healthz` при деплое.
На этапе 1 на него вешается Steam OpenID callback, на этапе 6 он вырастает в дашборд.
Один компонент, три применения.

Требование инфраструктуры: публичный URL с TLS (домен на VPS, сертификат через Caddy).

Поток: `/link steam` → бот создаёт запись в `account_verifications` с nonce и отдаёт
ephemeral-ссылку → пользователь логинится у Steam → callback проверяет подпись OpenID
и nonce → создаётся `game_accounts` с `verified_at`.

### Правила работы с внешними API

**Rate limiting — условие выживания ключа, а не оптимизация.** Riot применяет два окна
одновременно (секундное и двухминутное) плюс лимиты на метод и присылает `Retry-After`.
Token bucket в Redis на каждого провайдера, соблюдение заголовков ответа. Нарушение —
отзыв ключа.

**Пользователь никогда не ждёт внешний API.** Redis-кэш в режиме
stale-while-revalidate: отдаём имеющееся, обновляем в фоне. TTL фиксированы, чтобы при
реализации не выбирались наугад:

| Данные | TTL | Отдавать просроченное |
|---|---|---|
| Профиль (persona, аватар, библиотека) | 24 ч | до 7 суток |
| Ранг | 20 мин | до 24 ч |
| История матчей | 5 мин | до 1 ч |

**Circuit breaker.** Провайдер недоступен — показываем кэш с честной подписью
«данные на 14:32, Riot недоступен». Без спиннера и без шторма ретраев.

**Ранги обновляет планировщик, а не пользователь.** Cron-джоба запускается каждые
30 минут, берёт пачку до 100 аккаунтов с самым старым `updated_at`, обходит их с
задержкой между вызовами по бюджету token bucket и публикует `rank.changed` при
изменении — авто-роли подтягиваются сами. Обновление по запросу выело бы дневной лимит
за час.

Числа, зафиксированные во избежание произвола при реализации: челлендж верификации живёт
**15 минут** и допускает **5 попыток**; `/ranksync` доступен пользователю **раз в
10 минут**; таймаут внешнего вызова — **5 секунд**, до **3 попыток** с экспоненциальной
задержкой; circuit breaker открывается после **5 подряд** сбоев провайдера и пробует
снова через **60 секунд**.

Все внешние вызовы идут через один HTTP-клиент: таймаут, ретраи с экспоненциальной
задержкой и джиттером, обязательный `AbortSignal`, zod-валидация ответа.

### Команды этапа 1

| Команда | Действие |
|---|---|
| `/link steam` | привязка через Steam OpenID |
| `/link riot <riot-id> <region>` | привязка LoL/TFT: `third-party-code` или ручной fallback |
| `/link valorant <riot-id> <rank>` | привязка Valorant: ранг с ручного ввода, без верификации |
| `/unlink <provider>` | отвязка аккаунта, снятие выданных ролей |
| `/profile [user]` | карточка: привязанные аккаунты, текущие ранги, изменение за 30 дней |
| `/ranksync` | ручной запуск синхронизации своих рангов (кулдаун 10 минут) |
| `/admin rolemap set <provider> <mode> <tier> <role>` | настройка авто-ролей |
| `/admin rolemap list` | текущие маппинги |

Карточка профиля рендерится на Components V2 (флаг `MessageFlags.IsComponentsV2`).
Ограничения, которые надо учесть в вёрстке: с этим флагом нельзя использовать `content`
и `embeds` в том же сообщении, а контейнер держит максимум 10 компонентов.

## 6. Ошибки и надёжность

### Три класса ошибок

| Класс | Судьба |
|---|---|
| `UserError` | текст показывается пользователю как есть (ephemeral) |
| `ProviderError` | «внешний сервис недоступен» + данные из кэша с отметкой времени |
| `BugError` | пользователю код инцидента `ab12cd`, в лог — полный стек с тем же кодом |

Router оборачивает каждый хендлер. Наружу не проходит ничего необработанного.

### Три секунды на ответ интеракции

Discord закрывает окно ответа через 3 секунды. Всё, что может занять дольше — то есть
любой вызов внешнего API — обязано первым делом вызвать `deferReply()`. Это причина №1,
по которой боты выглядят молчащими, поэтому она закладывается в шаблон хендлера, а не
вспоминается каждый раз.

### Прочее

- **Идемпотентность компонентов.** `customId` несёт версию и владельца: чужие нажатия
  отклоняются, повторные не дублируют эффект.
- **Логи.** pino, JSON, обязательные поля `guild_id`, `user_id`, `command`,
  `correlation_id`. Без корреляции отладка невозможна.
- **Метрики.** `/metrics` в формате Prometheus: латентность команд, доля ошибок
  провайдеров, размер очереди синхронизации. Двадцать строк кода.
- **Graceful shutdown.** SIGTERM → перестаём принимать новое, доигрываем текущее,
  закрываем пул и Redis. Иначе каждый деплой рвёт живые интеракции.
- **Конфиг валидируется на старте.** Отсутствующий или битый env-параметр роняет процесс
  немедленно с понятным сообщением, а не через час в случайном месте.

## 7. Тестирование

| Уровень | Что покрывает | Инструменты |
|---|---|---|
| Unit | нормализация рангов, маппинг ролей, парсинг ввода, чистая логика сервисов | vitest, без сети и Discord |
| Интеграционные | репозитории, ограничения схемы, миграции | vitest + Testcontainers, **реальный Postgres** |
| Провайдеры (моки) | разбор ответов API, обработка ошибок и лимитов | записанные настоящие ответы |
| Контрактные | совпадение формата живых API с ожиданиями | по расписанию, бьют по реальным API |
| Хендлеры | что именно бот ответил на интеракцию | фейковый объект interaction |

Интеграционные тесты идут на реальном Postgres, а не на моке: значительная часть
ошибок живёт в SQL и ограничениях схемы, и мок их не воспроизводит.

**Контрактные тесты обязательны.** Это единственное, что ловит день, когда Riot поменял
формат ответа. Без них бот однажды сломается тихо.

Нормализация рангов пишется через TDD — там больше всего краевых случаев (сезонный сброс,
снятый ранг, unranked, отсутствие данных), и в тесте они дешевле, чем в проде.

Discord-слой не мокается целиком: тестируются хендлеры на фейковом interaction с
проверкой отправленного ответа.

## 8. Деплой

- **Docker multi-stage.** Сборка отдельно, рантайм-образ без dev-зависимостей.
- **Compose из четырёх сервисов:** бот, postgres, redis, caddy.
- **Миграции — отдельный шаг перед стартом бота**, не при первом запросе.
- **Slash-команды регистрируются guild-scoped скриптом** (`npm run deploy-commands`):
  применяются мгновенно, в отличие от глобальных с часовым кэшем.
- **Бэкап Postgres:** `pg_dump` по cron в объектное хранилище. Потеря базы означает
  безвозвратную потерю уровней и экономики.
- **CI (GitHub Actions):** eslint, `tsc --noEmit`, тесты на каждый push.
- **Секреты только через env.** Ни один токен не попадает в репозиторий.

## 9. Риски

| Риск | Вероятность | Влияние | Реакция |
|---|---|---|---|
| Riot не выдаёт production-ключ | средняя | Riot-фичи не работают | этап 1 сдаётся на Steam; Riot включается по факту |
| `third-party-code` выпилен вместе с `encryptedSummonerId` | средняя | нет верификации Riot | fallback на ручной ввод с пометкой «не подтверждено» |
| Приватные настройки Steam скрывают историю матчей | высокая | нет статы Dota у части игроков | явное сообщение с инструкцией, что открыть |
| Утечка памяти в модуле роняет процесс | низкая | бот недоступен | границы ошибок на модуль, healthcheck, авторестарт |
| Скоуп расползается на этапы 2–6 раньше срока | высокая | ничего не доделано | отдельный спек на каждый этап, никакого кода вне текущего |

## 10. Критерии готовности

### Этап 0

- Бот подключается к серверу, `/ping` отвечает с латентностью.
- `npm run dev` поднимает окружение целиком одной командой.
- Миграции применяются и откатываются на чистой базе.
- Битый env роняет процесс на старте с понятным сообщением.
- `/healthz` и `/metrics` отвечают.
- Модуль `ping` покрыт unit-тестом на фейковом контексте.
- CI зелёный: lint, typecheck, тесты.
- Compose-стек поднимается на VPS, бот выживает рестарт контейнера.
- SIGTERM завершает процесс без обрыва активной интеракции.

### Этап 1

- `/link steam` проходит OpenID и создаёт подтверждённый аккаунт.
- Повторная привязка того же Steam к другому Discord отклоняется с внятным текстом.
- `/link riot` работает при наличии ключа; без ключа — понятная ошибка, не стек.
- `/profile` показывает аккаунты, текущие ранги и изменение за 30 дней.
- `/profile` отвечает быстрее секунды на кэше и делает `deferReply()` при промахе.
- Недоступность Riot даёт карточку из кэша с отметкой времени, а не ошибку.
- Cron-синхронизация обновляет ранги и не превышает лимиты провайдеров.
- `rank.changed` приводит к выдаче и снятию ролей по `role_mappings`.
- `/link valorant` сохраняет ручной ранг, помечает его как заявленный игроком и не
  включает аккаунт в фоновую синхронизацию.
- `/unlink` снимает выданные роли и пишет запись в `audit_log`.
- Неподтверждённый аккаунт не получает авто-роль.
- Контрактные тесты провайдеров проходят по живым API.
